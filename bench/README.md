# 設計依存検知ベンチ

BDD の「要件は設計に依存しない」を機械で検知する手法の精度比較。in-browser で使う想定の
multilingual-e5 を Node で同条件計測し、**より大きなモデル（= remote provider）への差し替えが
必要かを判断する**ための計測。

## 手法

各文を文埋め込みにし、`score = max_i cos(text, 設計アンカー_i) − max_j cos(text, 業務アンカー_j)`
（最大類似度差）を計算。`score > threshold` で設計依存と判定する。重心差より margin が厚く頑健
（実使用のフィードバックで重心差→最大類似度差へ変更）。アンカーには UI/操作だけでなく、
データモデル・型（decimal 型・カラム・主キー・正規化）、インフラ（デプロイ・ロードバランサ・キュー）、
認証認可・アクセス制御（ロール・トークン・セッション）の設計依存も含める。アンカー・閾値・モデルは
`app/src/designModel.json` に置き、アプリ（in-browser）とこのベンチで共有する。

- regex: 語彙マッチ（旧実装の IMPL と同等）。
- multilingual-e5-small: in-browser 採用（量子化 ONNX 約120MB）。
- multilingual-e5-base: より大きいモデル（約4倍）。remote/上位モデルの代理。

## データ

`dataset.jsonl`（73件、設計依存=41 / 非依存=32、日本語の要件文）。手作りの小規模ベンチ。
設計依存側には、語彙マッチが取りこぼす言い換え（UI 操作・データモデル/型・インフラ・認証認可）を含める。
非依存側には、金額/在庫/残高など数値に触れる業務ルールや、役職・担当・承認といった業務の認可ルール
（「ロール」等の設計と紛らわしいが設計非依存）も入れて誤検出が出ないか見る。

## 実行

```bash
cd bench
npm i              # @huggingface/transformers（初回はモデルを自動DL）
node run.mjs       # 結果を RESULTS.md に書き出す
```

## 結果（`RESULTS.md`、threshold=0）

| 手法 | Precision | Recall | F1 | /text |
|---|---|---|---|---|
| regex（現行） | 100% | 34% | 50.9% | 0ms |
| e5-small（最大類似度差） | 100% | 93% | 96.2% | ~3ms |
| e5-base | 100% | 98% | 98.8% | ~12ms |

## 結論：in-browser の e5-small で運用可。provider 差し替えは任意

- 計測は browser と同じ量子化（q8、`DTYPE=q8`）で行う（fp32 より honest）。
- regex は precision は高いが recall 34%。言い換えの設計依存（UI 操作・型設計・インフラ・認可とも）を大量に取りこぼす。
- in-browser の e5-small は閾値0.005（q8）で **precision 100%（誤検出0）・recall 93%・F1 96.2%**。フラグのみの
  advisory には十分実用的で、特に誤検出ゼロは「無駄なフラグで信頼を損なわない」点で重要。最大類似度差＋
  分野別アンカー（UI/データモデル/インフラ/認可）で、「金額フィールドは decimal とする」「ユーザーはロールを持つ」
  なども拾え、かつ「役職ごとに承認上限」「経理担当だけが確定」などの業務認可ルールは誤検出しない。
- e5-base は F1 98.8% で recall が僅かに高い（取りこぼし1件）。小モデルとの差は recall（93→98%）で、約4倍の
  DL とリモート基盤に見合わない。
- よって **既定は in-browser の e5-small** とし、provider 抽象（差し替え口）だけ残す。recall を上げたい
  ときに e5-base / remote へ差し替えられる。

## 注意（この計測の限界）

- 73件・単一作者の小規模ベンチ。ドメイン（経費/在庫/会員/データ設計/インフラ/認可など）に偏りがある。
- スコアは0付近の狭い帯に固まり（設計≈+0.05〜+0.15、業務≈−0.05〜−0.16、境界の弱い文は±0.01）、設計文と
  業務文が0近傍で一部重なる。完全分離する閾値は無く、recall と誤検出はトレードオフ。browser(q8)と node の
  量子化差で0付近のスコアが±0.01程度ぶれるため、閾値は margin を取って 0.005（観測された境界誤検出 ~0.001 を抑える）。
- そのため弱い/短い言い換えは取りこぼしうる（recall 93%）。重要な検知漏れが許容できない用途では
  閾値を下げる（誤検出は増える）か、e5-base / remote（margin が広い）を検討する。
- best 閾値は test 上で最適化した楽観値。アプリは a-priori な閾値0.005（誤検出0寄り）を使う。
